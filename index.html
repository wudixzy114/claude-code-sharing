整体分五层：模型只出主意，runtime 才真把事办了

别把 Claude Code 想成一个更大的 Prompt。模型只生成「下一步说啥、调哪个工具」；把它变成动作、喂回结果、管好状态和权限的，是外面这五层——你从哪个入口进来走的都是它。

L5 入口分发cli.tsx
10+ 运行模式，统一入口命令行 REPL / IDE 插件 / SDK / 网页 Bridge / 无头 -p ——先在这里分流，后面共用同一套核心
L4 交互渲染React + Ink
把过程一个字一个字画到终端流式输出、diff、你的输入 / 中断 / 历史，都在这层
L3 编排QueryEngine
那个 while(true) 循环（约 46KB「God Object」）用 AsyncGenerator 一轮轮吐：搭上下文 → 问一次模型 → 跑工具 → 接着来或结束（第二章展开）
L2 能力tools · commands · skills
40+ 内置工具、50+ 斜杠命令、Skill读写文件、跑 Shell、搜索、派子任务——每样都要先过校验和权限
L1 基础设施state.ts · API · MCP
全局状态（60+ 字段）、API 客户端、MCP 通信、持久化会话状态跨很多轮一直存着，撑起上面四层
它为什么能稳？全局状态 state.ts 被强制做成依赖图的叶子节点（被 200+ 文件导入，用 ESLint 规则 bootstrap-isolation 卡住）。就因为状态和逻辑分得干净，中途压缩、失败重试、开子任务才不会把整盘搞乱。

五个入口怎么汇到一套核心？谁是核心、谁是插件？

上半：不管你从哪个入口进，最后都汇到同一个 QueryEngine——靠的是「入口适配器矩阵」。下半：接进来的东西按信任级别分轨，别把它们当成一回事。

入口适配器矩阵：核心引擎对入口「无感知」
入口传输权限 / 状态适配
REPLstdin/stdout用户确认对话 · 完整 React 状态树
MCPstdio空权限上下文 · 无状态 LRU
SDKspawn + 结构化 IOSDK 控制协议 · 外部控制
BridgeWebSocket / SSE远程权限桥接 · 远程同步
只在三个维度适配：传输、权限、状态。核心的工具注册表和执行引擎一份、共用——所以行为在各入口一致。
核心 vs 插件：信任越低、隔离越强

内置工具 / 命令tools.ts 中心化注册

40+ 工具、50+ 命令，编译进主进程。不用自动发现——工具 description 是 Prompt 的一部分，要精确控制。核心 · 完全信任

Plugin模块级隔离

主进程内跑 + 策略过滤。中信任

MCP进程级隔离

外部系统，运行时动态注册到同一张工具表。低信任

Skill纯 Prompt

不执行代码，只是 System Prompt 的一段。高信任

Hook事件总线 · 27 节点

用 \0 复合键做命名空间隔离。你的命令 · 全权限

工具 / 命令编译进核心；MCP / Plugin / Skill / 外部 Hook 是运行时动态接入（分层与数字取自逆向材料，随版本变）02

数十万行 TypeScript，却要求秒开、流式输出不花屏。两条工程主线：启动只加载你这次真要用的，渲染只重画变了的。

配置读哪些、谁盖谁、改完要不要重启？

这几个问题最容易踩坑：同一条规则在不同项目表现不一样，多半是优先级和"合并还是覆盖"没搞清。

settings.json 五级优先级（高 → 低）
企业 managed组织下发的 managed-settings.json，放在系统级目录（macOS /Library/Application Support/ClaudeCode/），由 MDM 统一推送，谁都盖不掉
命令行参数本次启动临时指定，如 --permission-mode plan、--dangerously-skip-permissions（跳过所有确认）、--add-dir ../lib
项目本地 .claude/settings.local.json只你自己、不提交 git
项目共享 .claude/settings.json随仓库提交，团队共享
用户 ~/.claude/settings.json你所有项目的兜底
注意：权限规则走"合并"，不走"覆盖"。高优先级不会把低优先级整份盖掉；各层的 allow / ask / deny 叠加在一起生效。
改完要重启吗？大多不用
改什么生效方式
权限规则实时 · 热更新，改完即生效
Hook 配置实时 · 热重载，不用重启
model要重启 · 换模型需新会话
outputStyle要重启
CLAUDE.md 也分四层（跨会话长期记忆）
企业组织策略，优先级最高
~/.claude/CLAUDE.md你所有项目通用的个人习惯
./CLAUDE.md随仓库提交，团队共享
CLAUDE.local.md只你自己、不提交

项目指令：不只分层，还能「改到某类文件才生效」

承接上一页的配置文件——指令也一样有层级，而且比配置多一招：.claude/rules/ 条件规则，能让某条规矩只在你动某类文件时才进上下文。很多人没用过这个。

CLAUDE.md 四层：无条件加载（低 → 高覆盖）
企业 /etc/claude-code/CLAUDE.mdMDM 下发，最硬
用户 ~/.claude/CLAUDE.md个人全局，不进 git
项目 ./CLAUDE.md·.claude/CLAUDE.md进 git，团队共享
条件 .claude/rules/*.md命中 paths 才注入
私有 CLAUDE.local.mdgitignore，只你自己
@import 引用：CLAUDE.md 里可写 @./coding-standards.md 把别的文件拼进来——有防循环、限深度 5、符号链接安全三重防护。
条件规则：frontmatter 写 paths，按文件触发
# .claude/rules/frontend.md --- paths: - "src/components/**/*.tsx" - "src/hooks/**/*.ts" --- React 组件一律用函数组件，不用 class。 hooks 必须以 use 前缀命名。
只在改 src/components 下的文件时，这条规矩才进上下文；改后端时它根本不占位。这就是「最小权限」搬到 Prompt——尤其适合 monorepo 前后端分治，省窗口、也少让模型分心。
会变的进度放会话摘要，别塞永久指令；跟文件强相关的规矩用 rules + paths 按需触发（字段名取自逆向材料，随版本变）07

一轮上下文，是按什么顺序组装起来的？

大部分内容是你看不见的「隐式注入」：启动前缀 + 运行时按需。你真正手输的，只有中间那一小段。

01 · 启动前缀（隐式，看不见）

Claude Code 按顺序拼接

  1. 系统提示词 + 内置工具 schema + 环境 / git 信息
  2. CLAUDE.md 沿目录树从根到工作目录逐层拼：企业策略 → ~/.claude → 项目根 → 当前目录；同级里 CLAUDE.local.md 排在 CLAUDE.md 之后
  3. auto memory（MEMORY.md 前 200 行 / 25KB）
  4. 无 paths 的 .claude/rules/、Skill 名称+描述、MCP 工具名

这些全部拼接，谁也不覆盖谁；越靠工作目录的排越后、最后读到。CLAUDE.md 是系统提示词之后的一条 user 消息——终端里你看不到它。

工具结果太长怎么办？

第 07 页占用图里橙色 38% 就是这块，最容易膨胀。工具一调完就地整理，别只等后面的压缩兜底。

情况运行时怎么处理
太长（大日志 / 大文件）完整结果落到文件，只回一条带路径的引用，要用再按路径展开
太短 / 为空补一个明确信号（如 exit 0，无输出），别让模型以为工具没跑成
二进制 / 图片不塞原始字节，转成一句描述（多少字节、什么类型）
重复 / 刷屏日志去重、合并同类行，只留代表 + 计数
太长 · 落文件 + 留引用
# grep 命中 1,284 行，不整坨回填，而是： ↳ 已写入 /tmp/cc-grep-8f2.txt 1,284 处命中 · 需要就按此路径展开
太短 / 空 · 给明确信号
# 命令成功但没有 stdout，不回空串，而是： exit 0，无输出 # 搜索零命中，不回空，而是： 无匹配（0 处）
能无限膨胀的只有工具结果这一块；把它管住，窗口就稳了一大半11

压缩其实是两类做法 + 一个触发器，只有一类调模型

微压缩 microcompact旧工具结果就地截断 / 换引用 / 去重清除；缓存版走 cache_edits 删除还保住缓存命中本地 · 不调模型 · 最常做

autoCompact 触发器盯阈值(有效窗口−13k)/时间/请求被拒(PTL)，决定何时压：先微压，压完还超才升级全量只管何时压

聊太长会变差吗？会。那我能怎么管？

上下文接近有效窗口就会自动压缩，压缩就有可能丢细节。别全交给它自动，手上这几条命令要会用。

会不会影响质量？会。官方明确讲：很长的对话里，早期给的指令可能"被丢掉"。所以关键约束别只在开头说一次。
一段真实的自动压缩日志（本地实测）
# 接近有效窗口，触发自动压缩 autocompact: ... effectiveWindow=180000 # 先本地清掉旧工具输出，不够再发一次摘要请求 [API REQUEST] /messages source=compact Reactive compact: summarization returned API error # ↑ 这次摘要请求失败了 → 会话继续涨 # → 下一次输入就报 Prompt is too long
有效窗口 = 配置值与模型最大窗口的较小值。不是你把窗口调大就一定生效。
四条你随时能用的命令
/context看窗口被谁占了、还剩多少，先诊断再动手
/compact [关注点]手动压一次，还能指定重点保留哪块，比等它自动压更可控
/clear清空当前对话历史，但保留 CLAUDE.md 里的项目记忆

① 合并，不是覆盖

一条 Bash 命令，是被拆开来判的

上页 echo "$(cat .env)" 为什么被拦？因为 Bash 不拿整行撞规则——先剥壳、再拆成子命令，每一段都要单独过，一段不过整条不过。

① 先剥掉包装前缀

timeout time nice nohup stdbuf command builtin xargs 会被剥掉，拿里面真正的命令去判。想用 timeout rm -rf / 绕过？剥完照样撞熔断。

② 拆复合命令，逐段匹配

&& || | ; 和命令替换 $(…) <(…) 全部拆开。任何一段不过，整条就不过——echo "$(cat .env)" 里 echo 无害，但内联的 cat .env 命中了 deny，于是整条被拦。

③ 只读内建：不用问

ls cat echo pwd head tail grep find wc which diff stat du + 只读 git，直接放。但一旦和危险段复合，这条豁免就不算数了。

④ 通配符看边界
规则写法能匹配到
Bash(ls:*)ls / ls -la —— :* 是前缀
Bash(ls)只精确 ls；ls -la 不算
deny Read(./.env)顺带盖住 cat/head/tail/sed .env
一句话：常见的绕过花招（换个包装、藏进管道、用等价读法），基本都被这套"剥壳 + 拆段 + 逐段过"堵住了。
把整行拆成一段段单独判，是 Bash 权限最容易被误解、也最关键的一环22

Hook 就是在流程的固定节点上，插一段你自己的命令——确定性执行，不靠模型判断，改完热重载不用重启。很多人不知道有这东西可用。

常用的生命周期事件
事件什么时候触发
PreToolUse工具执行前 · 可返回 allow / deny / ask
PostToolUse工具执行后 · 常用来跑格式化 / 测试
UserPromptSubmit你回车提交后、模型看到前
Stop / SubagentStop主任务 / 子任务收工时
PreCompact / SessionStart压缩前 / 会话开始时
配置在 settings.json —— 改完文件自动跑 prettier
"hooks": { "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "prettier --write $CLAUDE_FILE_PATHS" }] }] }
另外两个高频场景：
· PreToolUse 匹配 Read → 命中 .env 就 deny，守住密钥
· PreToolUse 匹配 Bash → 命中 rm 就 ask，危险命令二次确认

Hook 到底是干什么的？为什么要用它？

你会问的一句话回答
是干什么的？在流程固定节点插一段你自己的命令，到点必跑
为什么要用？模型可能忘记或选择不做；Hook 是确定性触发，不靠它判断
什么时候需要？需要"每次都必须发生"的事：见下方场景
能实现的四个特点
① 确定性执行（到点必跑）　② 生命周期拦截（PreToolUse 可 allow/deny/ask）
③ 能往上下文注入内容（如把 git 状态喂给模型）　④ 改完热重载，不用重启
典型场景：提交前 lint · 改完自动格式化 · 守住 .env 密钥 · rm 二次确认 · 审计留痕。
重点：Hook 本身有权限限制吗？受 Claude Code 管吗？
不受限——这是最容易踩的坑。
Hook 以你账户的完整权限直接跑，没有二次确认弹窗，Claude Code 不沙箱、不替你拦。写进去的命令你自己负全责——一条 rm -rf 一样会执行。
它和权限系统的关系：
PreToolUse 跑在权限检查之前，能返回 allow/deny/ask 影响决策——但 allow 只是免掉弹窗，盖不过静态 deny（尤其组织 managed 的 deny 永远赢）。
结论：要做硬约束用权限系统（deny 规则）；Hook 适合做确定性动作与治理，别拿它当安全边界。
Hook = 你亲手写、到点必跑的命令；能力很大，安全责任也全在你29

exit code含义

其它非 0非阻断（只记录，不拦）

个人、团队、公司：三层配置怎么分工

大多数人只用过自己的 ~/.claude。其实配置分三层——个人偏好、团队规范、公司底线，各有各的文件、各决定进不进 git。

五层来源（高 → 低）
公司 managed-settings.jsonMDM 下发，最高，命令行也盖不掉
命令行参数本次会话临时覆盖
项目私有 .claude/settings.local.jsongitignore，只你本机
项目共享 .claude/settings.json进 git，团队共享
用户 ~/.claude/settings.json你的全局，不进 git
关键两点：公司 managed 是最高优先级，命令行也覆盖不了它；再加上「deny 规则恒赢、不受层级覆盖」，用户再怎么 allow 也回不来——两重保障守住安全底线。
公司 managed：强制 deny + 只信任 managed hook
# mac: /Library/Application Support/ClaudeCode/ # managed-settings.json（路径随 OS 变） { "permissions": { "deny": ["Read(./.env)", "Bash(curl:*)", "WebFetch"] }, "allowManagedHooksOnly": true }
开了 allowManagedHooksOnly，用户/项目/插件的 hook 全被忽略，只跑公司下发的 hook——防有人用 hook 绕治理。
个人放宽（.local，不进 git，不动团队文件）
# .claude/settings.local.json { "permissions": { "allow": ["Bash(npm run dev:*)"] } }
公司 managed 优先级最高 + deny 恒赢，双重守底线；团队规范进 git；个人偏好放 .local35

哪些进 git（团队共享）· 哪些留本地（个人）

多 Agent：子 Agent 怎么起、上下文怎么不打架

起子 Agent 有两种玩法，差别就在"子 Agent 能不能看见你的对话"。子任务干完，回来的只有一段结论，不是它一路的流水账。

派个替身（Fork）

源码 forkSubagent.ts 的 buildForkedMessages()：把主对话整段历史复制给子 Agent，再附一条 directive 说"你去干这个"。子 Agent 拿到自己独立的 QueryEngine 循环，连你读过的文件缓存都克隆一份。

  • 模型：inherit——跟你用同一个，免得切模型把 prompt cache 冲掉
  • 适合：几路并行搜索、独立审查这种"带着同样背景各干各的"

调度 + 工人（Coordinator）

源码 coordinatorMode.ts，靠 COORDINATOR_MODE 开关开。调度只管拆活、拼结果，工人看不到调度的对话——所以给工人的 prompt 必须自包含。

  • 适合：阶段分明、结果能结构化拼起来的流程
  • 隔离更狠：信息不外泄，好局部重试
结果怎么回来：子 Agent 干完，只把最终那段结论用一条 <task-notification> 回传（就一个 <result> + 用量统计），不会把它一路的对话历史并回主线——这正是"保护主上下文不被撑爆"的关键。
两条要记的红线：
· 成本：N 个 fork 天真算就是 N 倍上下文；靠 prompt cache 前缀对齐共享省掉大头（材料称最多省 ~90% 输入成本）
· 深度只有一层：fork 出来的子 Agent 不能再 fork（报错 "Fork is not available inside a forked worker"），防无限递归
子 Agent = 独立上下文的替身；回来的是结论不是流水账，代价是复制上下文38

多 Agent：什么时候真该拆，怎么定义自己的子 Agent

拆之前先过三关（答不上就串行）
1. 子任务真独立吗？
老得共享状态、互相等，串行反而稳。
2. 输出有约定吗？
回来该是结构化的结论 / 证据 / 待办，不是一段散文——因为主线只收那一段 result。

一个子任务倒了，别把整盘历史和工具状态一起拖垮。

# .claude/agents/reviewer.md --- name: code-reviewer description: 审查改动，找 bug 和风险 tools: [Read, Grep, Bash] model: sonnet --- # 下面正文就是这个子 Agent 的 System Prompt 你是资深评审，只看 diff，按约定格式输出结论。
