每问一次模型前，运行时先把历史捋一遍

上一页"准备"那步不是一下子完成的，是一条固定顺序的预处理管线：从便宜、不丢信息，逐级走到贵、开始丢信息。这一整条你完全看不见。

1从压缩边界起算只带上次压缩之后的消息，之前的已被摘要顶掉getMessagesAfterCompactBoundary
2工具结果设上限给工具结果的 token 花销封顶，大日志先在这压住applyToolResultBudget
3按需裁历史命中门控才动，局部裁掉一段旧历史snipCompactIfNeeded
4增量微压缩一点点合并旧内容，尽量不惊动整段microcompact
5上下文塌缩命中门控，把尾端旧结果换成引用applyCollapsesIfNeeded
6兜底自动压缩最贵、最后才触发，整段压成摘要 + 近期原文autocompact
它就是上一页"拐回来"那条岔路的实现：前五步都尽量本地处理、不惊动模型；只有第 6 步真需要发一次模型请求做摘要。所以越往右越贵，能在左边解决就不往右走。
这里只讲顺序和位置。四层压缩偏"用户能手动 /compact"的那套细节，留到记忆章第 10 页——那页能点着看。

一轮上下文，是按什么顺序组装起来的？

大部分内容是你看不见的「隐式注入」：启动前缀 + 运行时按需。你真正手输的，只有中间那一小段。

01 · 启动前缀（隐式，看不见）

Claude Code 按顺序拼接

  1. 系统提示词 + 内置工具 schema + 环境 / git 信息
  2. CLAUDE.md 沿目录树从根到工作目录逐层拼：企业策略 → ~/.claude → 项目根 → 当前目录；同级里 CLAUDE.local.md 排在 CLAUDE.md 之后
  3. auto memory（MEMORY.md 前 200 行 / 25KB）
  4. 无 paths 的 .claude/rules/、Skill 名称+描述、MCP 工具名

这些全部拼接，谁也不覆盖谁；越靠工作目录的排越后、最后读到。CLAUDE.md 是系统提示词之后的一条 user 消息——终端里你看不到它。

→
02 · 人发起一轮（显式，唯一看得见）

你手输的这一段

  • 当前任务、补充要求、确认或纠正
  • 粘贴的文本、附件
  • 在 IDE 里显式选中的代码

整轮上下文里，这一段才是人直接提供、你自己看得见的内容。

→
03 · 运行时按需（隐式，看不见）

命中 / 调用才补进来

  1. 子目录 CLAUDE.md：读到该目录下的文件才加载
  2. 带 paths 的规则：命中匹配文件才触发
  3. Skill 正文：被调用时才载入（渐进式披露）
  4. MCP 完整 schema：tool search 按需拉取
  5. system-reminder、工具执行结果、模型回复

它们在你输入前都不在场，进来后就成了要管理的会话内容。

一句话记住：01 和 03 两段隐式内容，终端里几乎都看不到，却占了上下文一大半；人真正手输的只有中间 02 那一小段。想省上下文，先盯住隐式这两段。
CLAUDE.md 走「拼接」不走「覆盖」；子目录规则、Skill 正文、完整工具 schema 尽量留在运行时按需阶段08

工具结果太长怎么办？

情况运行时怎么处理
太长（大日志 / 大文件）完整结果落到文件，只回一条带路径的引用，要用再按路径展开
太短 / 为空补一个明确信号（如 exit 0，无输出），别让模型以为工具没跑成
二进制 / 图片不塞原始字节，转成一句描述（多少字节、什么类型）
重复 / 刷屏日志去重、合并同类行，只留代表 + 计数
太长 · 落文件 + 留引用
# grep 命中 1,284 行，不整坨回填，而是： ↳ 已写入 /tmp/cc-grep-8f2.txt 1,284 处命中 · 需要就按此路径展开
太短 / 空 · 给明确信号

聊太长会变差吗？会。那我能怎么管？

上下文接近有效窗口就会自动压缩，压缩就有可能丢细节。别全交给它自动，手上这几条命令要会用。

会不会影响质量？会。官方明确讲：很长的对话里，早期给的指令可能"被丢掉"。所以关键约束别只在开头说一次。
一段真实的自动压缩日志（本地实测）
# 接近有效窗口，触发自动压缩 autocompact: ... effectiveWindow=180000 # 先本地清掉旧工具输出，不够再发一次摘要请求 [API REQUEST] /messages source=compact Reactive compact: summarization returned API error # ↑ 这次摘要请求失败了 → 会话继续涨 # → 下一次输入就报 Prompt is too long
有效窗口 = 配置值与模型最大窗口的较小值。不是你把窗口调大就一定生效。
四条你随时能用的命令
/context看窗口被谁占了、还剩多少，先诊断再动手
/compact [关注点]手动压一次，还能指定重点保留哪块，比等它自动压更可控
/clear清空当前对话历史，但保留 CLAUDE.md 里的项目记忆
# 一句话随手把一条规则/结论写进记忆文件，下次开会话还在
落地建议：长任务别指望它自动记住关键结论。重要的用 # 写进 CLAUDE.md；快到上限时优先手动 /compact 并带上关注点。

你在哪授的权换个场景还算数吗
Bash "不再问"算 · 写进 .claude/settings.local.json，同一仓库跨会话都记得

粒度：能精确到命令前缀、目录、参数
# .claude/settings.json —— 按需自定义 "permissions": { "allow": ["Bash(npm test:*)", "Edit(src/**)"], "ask": ["Bash(git push:*)"], "deny": ["Read(./.env)", "Bash(rm -rf:*)"] }
记住：多层规则是"合并"的。各来源的 allow/ask/deny 叠加，deny 永远最硬。不确定当前生效哪条，用 /permissions 看。
能管到命令前缀、目录、参数这一级；跨会话记不记得，取决于写进了哪个文件14

安全和好用，不是二选一

按风险分三条通道：低风险走得飞快，高影响必须拦一下。这样既不烦人，又不失控。

低风险
尽量顺
搜代码、读项目文件、限定范围内分析 —— 这类应该几乎无感，别拿确认打断你。
常规
一次授权
项目内改动、跑测试 —— 基于明确的项目授权，别每次都重复问同一件事。
高影响
必须拦
改配置、访问网络、发布、删除、跨系统写入 —— 提高确认门槛，留审计，收紧范围。
一条产品经验：权限体验必须能解释、能只授权最小范围、能撤回。否则用户嫌烦，最后一律"全部放开"——你设计的那套治理就等于没有。
治理不是把它关笼子里，是让它能真正进到线上环境干活15

Hook：那些"能用却没人知道"的生命周期点

Hook 就是在流程的固定节点上，插一段你自己的命令——确定性执行，不靠模型判断，改完热重载不用重启。很多人不知道有这东西可用。

常用的生命周期事件
事件什么时候触发
PreToolUse工具执行前 · 可返回 allow / deny / ask
PostToolUse工具执行后 · 常用来跑格式化 / 测试
UserPromptSubmit你回车提交后、模型看到前
Stop / SubagentStop主任务 / 子任务收工时
PreCompact / SessionStart压缩前 / 会话开始时
配置在 settings.json —— 改完文件自动跑 prettier
"hooks": { "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "prettier --write $CLAUDE_FILE_PATHS" }] }] }
另外两个高频场景：
· PreToolUse 匹配 Read → 命中 .env 就 deny，守住密钥
· PreToolUse 匹配 Bash → 命中 rm 就 ask，危险命令二次确认
Hook 是"到点必执行"的确定性规则，适合做治理；别拿它当模型的替代品17

Hook 到底是干什么的？为什么要用它？

你会问的一句话回答
是干什么的？在流程固定节点插一段你自己的命令，到点必跑
为什么要用？模型可能忘记或选择不做；Hook 是确定性触发，不靠它判断
什么时候需要？需要"每次都必须发生"的事：见下方场景
能实现的四个特点
① 确定性执行（到点必跑）　② 生命周期拦截（PreToolUse 可 allow/deny/ask）
③ 能往上下文注入内容（如把 git 状态喂给模型）　④ 改完热重载，不用重启
典型场景：提交前 lint · 改完自动格式化 · 守住 .env 密钥 · rm 二次确认 · 审计留痕。
重点：Hook 本身有权限限制吗？受 Claude Code 管吗？
不受限——这是最容易踩的坑。
Hook 以你账户的完整权限直接跑，没有二次确认弹窗，Claude Code 不沙箱、不替你拦。写进去的命令你自己负全责——一条 rm -rf 一样会执行。
它和权限系统的关系：
PreToolUse 跑在权限检查之前，能返回 allow/deny/ask 影响决策——但 allow 只是免掉弹窗，盖不过静态 deny（尤其组织 managed 的 deny 永远赢）。
结论：要做硬约束用权限系统（deny 规则）；Hook 适合做确定性动作与治理，别拿它当安全边界。
Hook = 你亲手写、到点必跑的命令；能力很大，安全责任也全在你18

怎么给我的 Claude Code 加 Hook？三步

直接回答"具体怎么操作"：选作用域 → 写结构 → 存盘即生效。全程就是编辑一个 settings.json。

第 1 步　选作用域，打开对应的 settings.json
# 只给自己用（所有项目） ~/.claude/settings.json # 给团队共享（提交 git，进版本库） .claude/settings.json # 只本机本项目（不提交，覆盖上面） .claude/settings.local.json
优先级高到低：managed（组织） → local → project → user；权限规则是合并不是整个覆盖。
第 2 步　按结构写：事件 → matcher → command
"hooks": { "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "my-guard.sh" }] }] }
my-guard.sh 从 stdin 读到 tool_input；命中 rm 就 exit 2 阻断（stderr 会回给模型），否则 exit 0 放行。
第 3 步　保存即生效（热重载，不用重启）
存盘就生效。下一次触发该事件时，你的命令就会跑起来——改错了改回来也是当场生效。
想看已经注册了哪些 Hook？
/hooks # 会话里直接输
注意：/hooks 是只读浏览器。只能查看已注册的事件与命令，不能在里面加——要加还是回去编辑 settings.json（或直接让 Claude 帮你写进去）。
退出码语义（决定放行还是阻断）
exit code含义
0成功放行；stdout 可回填上下文
2阻断，stderr 内容回给模型
其它非 0非阻断（只记录，不拦）
再强调一次：Hook 以你的完整权限跑、无确认——别把没验证过的命令写进去。
加 Hook = 编辑 settings.json 的三步；/hooks 只能看，加靠改文件19

Skill 到底怎么写？最小就是一个目录 + 一个文件

最小结构：目录名 = 命令名（/summarize-changes）
# 用户级（所有项目可用） ~/.claude/skills/summarize-changes/SKILL.md # 项目级（仅本项目，可提交 git） .claude/skills/summarize-changes/SKILL.md
--- name: summarize-changes # 可选，默认取目录名 description: 总结未提交改动并标记风险。 当用户问"改了什么"、要 review diff 时使用。 --- !`git diff HEAD` # !反引号=先执行命令，输出注入 用 2-3 条要点总结上面的改动，并列出风险。
只有 description 建议必填。它决定 Claude"什么时候该用这个 skill"，写清触发场景很关键。
怎么被"按需触发"（渐进式披露）：平时只把每个 skill 的名字 + description 放进上下文；完整 body 只在被调用时才载入。所以长参考资料不用时几乎零成本——就是记忆章第 08 页那套注入机制。改完 SKILL.md 当场生效，不用重启。

MCP：一条命令，把外部系统接成工具

MCP 把知识库、工单、数据库这些外部系统，包成 Claude 能统一调用的工具。接入就一条 claude mcp add。

三种传输类型
# HTTP —— 远程，最推荐，支持 OAuth claude mcp add --transport http notion \ https://mcp.notion.com/mcp # stdio —— 本地进程，注意 -- 后才是启动命令 claude mcp add --transport stdio airtable \ --env KEY=xxx -- npx -y airtable-mcp # sse —— 已弃用，尽量改用 http
接完用 /mcp 看连接状态。工具名启动就在场，完整 schema 用到才加载。
作用域（-s / --scope）= 配置存在哪
作用域范围 / 存放
local
(默认)		仅你、仅当前项目 · 存 ~/.claude.json
project团队共享 · 写进项目根 .mcp.json，可提交 git（队友首次需 trust 批准）
user你的所有项目通用
要给团队共享：用 --scope project，把 .mcp.json 提交进仓库，队友拉下来就能用。
.mcp.json 里有 url 就必须写 type（http / sse），否则报错。
从个人到团队：.claude/skills、.claude/agents、.mcp.json 提交 git；跨项目复用就打成 Plugin 走 marketplace21

多 Agent：先问一句"这活真的能拆吗"

派个替身去干（Fork）

主任务带上必要的上下文，分出一个独立子任务，回头收结果。

  • 适合：并行搜索、局部测试、独立审查
  • 好：轻，起得快，和主任务像
  • 代价：要复制上下文，可能抢工具、结果打架、成本上去

一个调度多个工人（Coordinator）

调度的只管拆和汇总，工人只管干各自那块明确的活。

  • 适合：阶段清楚、结果能结构化拼起来的流程
  • 好：隔离更干净，结果更稳，好局部重试
  • 代价：编排复杂，要显式的任务图和汇总逻辑
1. 子任务真独立吗？
要是老得共享状态、互相等，串行反而更好。
2. 输出有约定吗？
该返回结构化的结论、证据、待解决项，不是一段散文。
3. 挂了能局部恢复吗？
一个子任务倒了，不该把整盘历史和工具状态一起拖垮。
Agent 更多不等于更聪明；并行是要付上下文和协调成本的23
