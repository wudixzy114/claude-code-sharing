先说结论：模型只出主意，跑起来靠外面那层

你让它"重构 parsePath 并跑测试"，它会走一圈又一圈：出主意 → 动手 → 看结果 → 再出主意。你感觉它在"连续干活"，其实是这个圈在转。

你的目标
重构这个函数，
别改坏，
跑测试证明没问题
模型出主意
看现在手里有什么信息，
决定先读文件还是先改
工具动手
真去读代码、改文件、
跑测试命令
拿回结果
改动、报错、测试日志
都成了新的线索
接着做 / 收工
还没弄完就再来一轮，
弄完了就汇报
模型负责
想下一步

看当前手里的信息，说出一段话，或者提出要调某个工具。仅此而已。

运行时负责
真把事办了

存状态、执行工具、处理报错、管好上下文和权限。这些模型自己做不了。

你看到的
它在连续干活

把它拆成五层看，不神秘

没有什么"神秘的智能大脑"，就是分工清楚的几层。你从哪个入口进来都走同一套。

入口你从命令行、IDE 插件、SDK 还是网页进来，后面都一样
界面和会话把过程一个字一个字显示出来，管你的输入、中断和历史
核心：那个循环会话状态：这一路的消息、用量、被你拒过的操作、缓存
单次调用：搭好上下文、问一次模型、跑工具、接着来或者结束
工具读写文件、跑 Shell、搜索、派子任务、连外部系统——都要先过校验和取消
横着贯穿的
上下文和记忆
配置和指令
权限和安全
Hook / MCP / 插件
最该记住这一点：会话状态是跨很多轮一直存着的，单次调用只管当前这一轮。就因为分开了，中途压缩、失败重试、开子任务才不会把整盘搞乱。
不用记模块名，记住谁负责什么02

一、循环
04 / 24

这一圈里它到底替我们干了啥？功夫全在岔路上

循环主干简单到你会失望。真正的工程质量，在"接着做、拐回来、停下来"这三种岔路怎么处理——这些平时对我们是不透明的。

开始你的输入 / 一个子任务 / 接着上次的会话
准备先看预算够不够
不够就先压缩
问一次模型流式吐出来
是文字还是要调工具
跑完塞回去工具结果
作为新消息加进历史
结束做完 / 你取消 / 预算用光 / 遇到修不了的错
接着做

模型要调工具
跑完把结果带进下一轮，再问一次。

拐回来

上下文太长了
先压缩腾出空间，再重新问模型。

纠偏

工具或测试挂了
把报错整理好丢给模型，让它判断怎么办。

停下来

你或策略叫停
把取消信号传下去，把正在跑的东西释放掉。

一句话：可靠靠的是"出了错也能被看见、能恢复、能干净地停下"。这就是 while(true) 和"真能干活的循环"的区别。
while(true) 不等于没有边界04
一、循环
05 / 24

"调工具"不是直接执行，是过一条流水线

模型只是提了个意图。运行时要把这个意图，变成一个有边界、能回放、出了事能查的操作。第 7 关"收拾结果"，直接决定你的上下文会不会被撑爆。

1认出来是哪个工具，参数是什么
2补齐补上工作目录、超时、默认值
3校验类型、路径、命令、能碰的范围
4查规则命中放行 / 要问 / 禁止
5要授权影响大的动作，先问你一句
6真跑隔离、超时、能取消、控并发
7收拾结果太长截断、太短给信号、脱敏、结构化
8归档写进会话、事件流和操作记录
改文件这一类：要管路径范围、几处同时改会不会冲突、写入是不是原子的、能不能回滚。
跑 Shell 这一类：要管在哪个目录跑、命令什么意思、超时、取消、输出太长怎么截。
好工具表达的是业务动作——发布、检索、变更，而不是"帮我执行任意命令"05
