一次任务如何真正跑起来

1. 准备加载项目指令、工具、工作目录与会话状态
2. 模型调用流式返回文本、思考后的行动意图或工具调用
3. 工具执行权限检查、执行、取消控制、结果标准化
4. 结果回填工具输出进入历史，成为下一轮新的证据
5. 结束判定自然完成、用户取消、预算用尽、不可恢复错误
“重构并验证”有新的行动需求就继续
没有工具调用或命中终止条件就结束
状态目标、历史、用量、文件缓存、权限拒绝记录
事件流文本增量、工具开始、工具结果、确认请求、错误与完成
恢复上下文超长、工具失败、测试失败都不是“崩溃”
停止每一条继续路径有理由，每个终止点有语义

专题二 · 上下文管理
07 / 18

四层渐进压缩：它“能无限续航”的真正机制

1. 引用替换大结果保留引用、路径、可按需展开的内容
2. 微压缩去重、截断冗余日志、合并连续结果
3. 会话记忆结构化记录决策、修改、验证、剩余风险
4. 语义折叠最后才压缩整段历史，保留摘要与近期原文

从低成本、低损失，逐步走向高成本、强压缩

A
先轻后重
引用和规则处理优先；模型摘要是昂贵且可能损失细节的最后手段。
B
保留四类锚点
用户目标、关键约束、已验证事实、未完成工作。它们决定下一轮是否还能正确接力。
C
可恢复、可追溯
摘要不是唯一事实源。必要时通过引用回查原始工具结果，防止“摘要漂移”。
D
防递归压缩
对同一段历史反复摘要会放大误差；系统需要识别压缩来源和触发原因。
无限不是“永远记住全部”，而是“始终记住下一步所需”07
专题二 · 上下文管理
08 / 18

Prompt 与项目记忆：每一轮到底该遵守什么

更好的做法不是“写一段更长的 Prompt”，而是把指令当作有优先级、可追踪的配置协议。

组织 / 管理规则安全红线、合规要求、不可覆盖的边界
系统与动态能力工具定义、当前环境、可用 Skill 与会话模式
项目级指令构建命令、测试门槛、目录边界、接口约束
个人偏好表达格式、局部工作习惯、临时偏好
→
当前轮有效上下文

稳定规则 + 环境能力 + 项目约定 + 当前任务摘要 + 最近关键证据

不要放：完整历史、变化中的进度、巨量日志。它们属于会话记忆和工具结果管理。

项目指令应短而硬：怎样构建、怎样验证、哪些目录不能碰、如何交付证据。
会话摘要应动态：已经做了什么、哪些结论被验证、下一步还有什么风险。
解决“同一句话在不同仓库表现不同”的关键，是层次与来源，不是更长的提示词08
专题二 · 上下文管理
09 / 18

上下文的四个反模式，与对应的团队解法

1

永久 Prompt 写成百科

每轮成本高，重点被淹没，变化信息过期。

解法：规则分层；永久指令只保留稳定、强约束的内容。

2

完整日志反复带入

工具输出消耗预算，却未必增加判断价值。

解法：截断、去重、引用替换和按需展开。

3

只摘要，不保来源

摘要一旦错了，系统无法纠正自己的“记忆”。

解法：摘要保留证据链接、文件位置与验证状态。

4

子 Agent 继承全部历史

并行时把成本和噪音同步放大。

解法：按任务给最小必要上下文和结构化输出契约。

优先建设：任务摘要格式、工具输出分级、项目指令层级、压缩后可回查机制。比“更长上下文”更早带来稳定性。
上下文管理决定长任务是否可信地续航09
专题三 · 权限与安全
10 / 18

权限不是弹窗，而是自动化的策略引擎

要同时满足效率和可信，需要把不同风险放到不同速度的通道。

低风险 / 明确规则

Allow

只读搜索、受限范围内的常规操作。

目标：尽量无摩擦，不让确认干扰正常探索。

影响明确但需确认

Ask

写入文件、运行命令、跨系统操作。

目标：把确认放在真正改变状态的边界。

不可接受 / 命中红线

Deny

敏感路径、危险命令、违反组织策略。

目标：明确阻断，并解释哪条规则命中。

受控的自动化模式

Auto

在限定范围与策略下减少重复确认。

目标：授权最小化、范围清晰、可撤销可审计。

决策输入不只是“这条命令”：工具类型、参数、路径、工作目录、项目规则、组织策略、会话模式和用户选择共同决定结果。
“允许 npm test”与“允许任意 shell”是两种完全不同的授权10
专题三 · 权限与安全
11 / 18

权限决策：先确定性规则，后处理语义灰区

工具调用请求工具名 + 参数 + cwd + 会话模式 + 当前策略
→
静态校验类型、路径、命令、资源范围。命中禁止规则即停止。
→
明确策略命中Allow 直接放行；Ask 请求确认；Deny 记录原因。
→
不确定的灰区可做语义辅助判断；解析失败、超时、不确定均走保守分支。
快路径
低风险、可枚举

只读工具和明确安全动作，不必每次调用模型分类器。

语义辅助
规则难覆盖的灰区

例如命令字面相似、实际影响不同的情况；它是补充层。

回退机制
拒绝过多就交给人

连续误判或分类器卡住时，停止自动化判断，恢复人工确认。

原则：确定性策略优先；AI 分类只能协助理解语义。安全系统面对异常时，默认选择更保守的一边。
好的权限系统输出“为什么”，而不仅是“允许 / 拒绝”11

低风险通道：代码搜索、读取项目文件、受限范围内的分析，应尽量无摩擦。

专题四 · 扩展架构
13 / 18

把团队能力接进闭环：三种扩展，不是一种

扩展系统的价值，是把正确的知识、工具和流程接到正确的生命周期节点。

Hook

在生命周期节点拦截、检查或追加动作。

  • 工具执行前：检查分支、敏感文件、变更范围
  • 工具完成后：格式化、测试、证据采集
  • 会话结束前：阻止未验证的交付

适合：规范与治理。重点是事件时机与失败语义。

MCP

将外部系统转成统一的 Agent 工具接口。

  • 代码索引、知识库、需求与工单
  • CI 状态、测试平台、内部服务
  • 认证、连接与故障恢复成为运行时责任

适合：系统集成。重点是工具语义、权限和可观测性。

Skill / Command / Plugin

把提示、流程、Agent 配置打包分发。

  • 按场景加载仓库规范与任务模板
  • 把重复工作变成可复用能力
  • 以版本化方式在团队传播

适合：工作流产品化。重点是组合、升级和治理边界。

别把“接得更多”当成扩展成功；每个工具都带来认证、权限、可用性和上下文成本13

专题五 · 多 Agent 取舍
15 / 18

多 Agent：先问“任务真的可拆吗？”

Fork-and-Delegate

父任务携带必要上下文，派生独立子任务并回收结果。

  • 适合：并行检索、局部测试、独立审查
  • 优点：轻量、启动快、子任务和父任务语义接近
  • 代价：上下文复制、工具竞争、结果冲突与成本膨胀

Coordinator-Worker

协调者只拆分和汇总；Worker 只执行明确工作单元。

  • 适合：阶段明确、输出可结构化聚合的流程
  • 优点：隔离更清晰、结果契约更稳定、易局部重试
  • 代价：编排复杂，需要显式任务图和汇总逻辑
1. 子任务独立吗？
若频繁共享状态、互相等待，串行通常更好。
2. 输出有契约吗？
应返回结构化结论、证据与未解决项，而非一段散文。
3. 能局部恢复吗？
一个子任务失败不应让全局历史和工具状态一起失效。
更多 Agent 不等于更聪明；并行是一种有上下文与协调成本的资源调度15
落地建议
16 / 18

如果要补齐能力，优先级应该是什么

先建设让单 Agent 稳定、可信、可进入团队系统的地基；多 Agent 是后续吞吐优化。

P0
项目指令与任务摘要

分层规则、结构化会话记忆、工具输出分级、压缩后可回查。

验收：新会话拿到摘要后，能准确说出目标、已验证结论、剩余风险和下一步。
P0
最小权限与审计

工具策略、确认体验、路径与参数约束、可解释的拒绝原因。

验收：授权范围最小；每次允许 / 拒绝可追溯到明确规则与操作记录。
P1
工具协议、MCP 与 Hook

统一外部工具接入；把测试、规范和证据收集插入正确节点。

验收：外部系统可观测、可降级；失败不会把 Agent 留在无解释的卡死状态。
P2
多 Agent 编排

定义任务图、上下文范围、结果契约和局部重试，验证真实收益。

验收：并行相较串行在时延、成本、成功率至少一个维度有可重复收益。
先让一个 Agent 做对、做稳、做得可控，再谈规模化并行16
复盘
17 / 18

用四个问题检查我们的 Agent 能力

1

循环

工具失败、用户取消、上下文超长时，我们的状态机是否有明确且可观察的恢复与终止路径？

2

压缩

长任务中，我们是否能保留目标、约束、事实与未完成项，而不是把完整日志或模糊摘要塞回去？

3

权限

我们是否能以最小授权执行动作，并解释“为什么允许、为什么拒绝、如何安全地放开一点”？

扩展

团队知识、测试、代码索引和交付规范，是否被接入正确生命周期，而非散落在提示词里？

判断标准：如果某项能力只能在演示里工作、无法解释失败、无法限制影响范围，它还不是可进入工程环境的 Agent 能力。
架构问题最终会反映为稳定性、成本、效率与可信度17
结语
18 / 18

Claude Code 的工程价值，
不在某一个神秘 Prompt。

它把模型放进了一套能够行动、能够续航、能够受控、能够接入真实工作流的运行时。
循环模型与工具构成可恢复、可终止的反馈闭环。
压缩把有限 token 分配给下一步真正需要的事实。
权限以可解释的分级策略换取可信自动化。
扩展在正确节点把团队系统和规范纳入流程。
